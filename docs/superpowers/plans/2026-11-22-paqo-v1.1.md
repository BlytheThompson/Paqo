# Paqo v1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the sensor recorder (with re-processing), sharper sprint detection, a smoothed route, sprint trends, the heatmap and replay, and readable automatic and manual backups to Paqo.

**Architecture:**
- Every new algorithm and file format lives in `PaqoCore`, which is pure Foundation and is built and tested on Windows.
- Sensors produce one ordered stream of `SensorEvent`s. A `SessionRecorder` sends each event through the log codec, so the logged value and the value the engine sees are bit-identical. It then writes the event to the sensor log and applies it to `RunEngine`. Replay and re-processing feed the same events through the same engine.
- The iOS layer only adapts sensors, files and UI. It is syntax-checked locally and compiled on CI.

**Tech Stack:**
- Swift 5 language mode (tools 5.10), Foundation, XCTest
- SwiftUI, MapKit for SwiftUI, Swift Charts
- CoreMotion: `CMMotionManager`
- XcodeGen, GitHub Actions `macos-26`

**Spec:** `docs/superpowers/specs/2026-11-22-paqo-v1.1-design.md`. Read it with this plan.

## Global Constraints

- **PaqoCore imports only Foundation.** Anything that touches an Apple framework goes in `PaqoSensors` (wrapped in `#if os(iOS)`) or in `App/`.
- **The engine is deterministic.** Engine code never calls `Date()`, never uses randomness, and never iterates a `Dictionary` or `Set` in a way that affects results.
- **Old files still decode.** New fields on persisted types (`LocationSample`, `Run`, `RunSegment`) are optional or use `decodeIfPresent` defaults, so v1 run files decode. `RunSummary` is the exception: its new `sprintStats` is non-optional on purpose, so an old `index.json` fails to decode and the existing rebuild runs.
- **Sensor logs:**
  - folder `Application Support/Paqo/sensor-logs/<run-id>/`, containing `meta.json` plus `gps.csv`, `activity.csv`, `pedometer.csv`, `altimeter.csv`, `accel.csv` and `events.csv`;
  - on by default;
  - kept for the last 20 runs;
  - accelerometer at 50 Hz.
- **Starting detection values:**
  - switch to sprint after 1.5 s, switch to walk after 2 s;
  - blip rules from v1: sprints under 5 s or under 15 m become walks, and walks under 5 s between sprints are merged into the sprint.
- **Peak speed** is the highest 2-second average speed.
- **Run fade** needs at least 3 sprints.
- **The fastest-sprint record** only counts sprints of at least 10 s.
- **Route filter gating:**
  - fixes with accuracy worse than 50 m are ignored;
  - fixes between 25 and 50 m are down-weighted;
  - GPS counts as poor (so the step-speed aid kicks in) when accuracy is worse than about 15 m.
- **Trends:**
  - ranges are 4 weeks, 3 months, 1 year and All;
  - buckets are weekly for 4 weeks and 3 months, monthly for 1 year and All;
  - tab order is Run, History, Trends, Records, Settings.
- **Replay** plays at 10×, 30× or 60×.
- **Heatmap:**
  - routes are simplified to a tolerance of about 5 m;
  - date filters are All, 1 year and 3 months;
  - there is a Sprints only switch.
- **Backup formats:**
  - CSV is UTF-8 with a BOM and RFC 4180 quoting;
  - JSON is `"format": "paqo-run", "version": 1`, pretty-printed, with ISO 8601 dates;
  - GPX is version 1.1;
  - zips are store-only (no compression).
- **Backup layout:** `Paqo Backup/README.txt`, `runs.csv`, `sprints.csv`, `runs/*.json`, `runs/*.gpx` and `deleted/`.
- **Auto-backup** only ever touches the run that changed. It never deletes anything outright; a deleted run's files move to `deleted/`.
- **Privacy:** real sensor logs and backups are never committed. They go in the gitignored `private/` folder. Test data is synthetic.
- **Cloud builds:** none until the owner gives the go-ahead. Commits stay local. Push only when the owner asks.

## Review Focus

These five situations are the ones most likely to hurt the owner that no feature test covers by itself. Each line names the expected behavior and the test that pins it.

1. **A run with no GPS fixes** (started indoors, or location turned off mid-run). It still finishes with distance 0 and a valid run, without crashing in the smoother or the re-segmenter. Test: `testRunWithNoFixesFinishesCleanly` (Task 6).
2. **A crash-recovered run that is then re-processed.** Its log has no `finish` event and may end in a half-written line. Replay skips the partial line and closes the run at the last activity, just as recovery does. Test: `testReplayOfCrashedLogIgnoresPartialLine` (Task 7).
3. **Run names with commas, quotes, newlines or emoji.** CSV parses back to the same fields, GPX and JSON escape them correctly, and file names never contain the name. Test: `testAwkwardNamesSurviveCSVAndGPX` (Task 12).
4. **A backup folder whose CSVs no longer match** (the owner switched units, or a CSV is corrupt). The CSVs are rebuilt from the folder's JSON files, never trusted blindly, and never rebuilt from the app's runs. Tests: `testUnitSwitchRebuildsCSVFromFolderJSON` and `testCorruptCSVIsRebuiltFromFolderJSON` (Task 13).
5. **A 3-hour run.** Finishing (smoother, re-segmenter and stats) stays fast enough that the summary appears without a visible hang. Test: `testThreeHourRunFinishesQuickly` (Task 6): `finish()` on 10,800 fixes takes less than 2 s in a debug build on Windows.

### Task 3: Step rhythm from the accelerometer

**Files:**
- Create: `PaqoKit/Sources/PaqoCore/StepRhythm.swift`
- Modify: `TestSupport.swift` (`SeededGenerator`, `syntheticAccel`)
- Test: `StepRhythmTests.swift`

**Interfaces:**
- Produces:
  - `public struct RhythmSample: Codable, Hashable, Sendable { timestamp: Date; cadence: Double?; periodicity: Double; intensity: Double }`. `timestamp` is the **centre** of the analysis window, `cadence` is in spm, and `intensity` is the RMS of the de-meaned magnitude, in g.
  - `public struct StepRhythmAnalyzer: Codable, Sendable { init(); mutating func ingest(_ batch: [AccelSample]) -> [RhythmSample] }`. It emits one sample per 0.5 s of sample time once 4 s are buffered.
- **Test support:**
  - `SeededGenerator: RandomNumberGenerator` (SplitMix64) with `gaussian() -> Double`.
  - `syntheticAccel(start: Date, seconds: Double, cadence: Double, impact: Double, asymmetry: Double = 1, noise: Double = 0.02, rng: inout SeededGenerator) -> [AccelSample]`. It samples at 50 Hz, with z = 1 + a Gaussian pulse (width 60 ms, height `impact`) at each step and every other step scaled by `asymmetry`; x and y are noise only.

- [ ] **Step 1: Write the failing tests**
  - `testFindsWalkingCadence`: 110 spm with impact 0.4. The median cadence over the last 10 samples is within ±3 of 110.
  - `testFindsSprintCadence`: 170 spm with impact 1.5. The median is within ±3 of 170.
  - `testDoesNotLockOntoStride`: 160 spm with asymmetry 0.7. The median is within ±3 of 160, not 80.
  - `testIntensitySeparatesSprintFromWalk`: the median intensity of the sprint signal is more than 2× that of the walk signal.
  - `testStillPhoneHasNoCadence`: noise only (impact 0). Every cadence is nil.
  - `testTimestampsAreWindowCentres`: the first sample's timestamp is about start + 2.0 s (±0.05).
- [ ] **Step 2:** Run `swift test --filter StepRhythmTests`. Expected: build failure.
- [ ] **Step 3: Implement.**
  - Buffer the magnitudes √(x²+y²+z²) for the last 4 s. Every 0.5 s, subtract the mean and compute `intensity` as the RMS.
  - Compute the normalised autocorrelation r(lag) for lags from 0.25 s to 1.0 s (240 to 60 spm), using the mean sample interval. Take the lag with the highest r and refine it with parabolic interpolation.
  - Anti-stride rule: if r at half that lag is at least 0.6 × r at the lag, and half the lag is still in range, use the half lag.
  - `cadence = 60 / period`. Set it to nil when the peak r is below 0.3 or `intensity` is below 0.03 g.
  - `periodicity` = the peak r.
- [ ] **Step 4:** Run `swift test --filter StepRhythmTests`. Expected: pass.
- [ ] **Step 5:** Commit: `feat(core): accelerometer step rhythm`.

### Task 4: Route filter (Kalman) and smoother (RTS)

**Files:**
- Create: `PaqoKit/Sources/PaqoCore/RouteFilter.swift`
- Test: `RouteFilterTests.swift`

**Interfaces:**
- Produces:
  - **`LocalFrame`:** `public struct LocalFrame: Codable, Sendable { init(origin: Coordinate); func toLocal(_ c: Coordinate) -> (east: Double, north: Double); func toCoordinate(east: Double, north: Double) -> Coordinate }`. It is a flat-earth projection using `Geo.metersPerDegree*` at the origin.
  - **`FilterMeasurement`:** `public struct FilterMeasurement: Codable, Hashable, Sendable`, with fields:

    - `stepSpeed`, `stepSpeedSigma: Double?`
    - `altitude: Double?`
  - **`FilterState`:** `public struct FilterState: Codable, Hashable, Sendable { east, north, velocityEast, velocityNorth: Double }`.
  - **`RouteFilter`:**
    ```swift
    public struct RouteFilter: Codable, Sendable {
        public struct Configuration: Codable, Equatable, Sendable {
            accelerationSigma = 2.5     // m/s²
            minPositionSigma = 3        // m
            gateChiSquare = 13.8        // 2 degrees of freedom, 99.9%
            maxConsecutiveRejections = 3
            zeroVelocitySigma = 0.05    // m/s
        }
        init(config:)
        mutating func update(_ m: FilterMeasurement) -> (state: FilterState, accepted: Bool)
        mutating func reset()
    }
    ```
  - **`RouteSmoother`:** `public enum RouteSmoother { static func smooth(_ measurements: [FilterMeasurement], config: RouteFilter.Configuration) -> [FilterState] }`. It returns one state per measurement, in the same order. It runs the forward filter again and then the RTS backward pass separately for each `line`.

- [ ] **Step 1: Write the failing tests**
  - Common setup: 300 s at 3 m/s going north, with position noise σ = 4 m from `SeededGenerator(seed: 7)`. The true distance is 900 m. Distance means the sum of distances between consecutive states.
  - `testSmoothedDistanceWithDopplerWithinOnePercent`: velocity measurement (0, 3) with σ 0.3 at every step. The smoothed distance is within ±9 m of 900.
  - `testSmoothedDistanceWithoutDopplerBeatsRaw`: no velocity. The smoothed error is less than 3% and less than half of the raw error.
  - `testZeroVelocityHoldsStill`: 60 s with noise and `zeroVelocity = true`. The smoothed distance is under 2 m.
  - `testOutlierIsRejected`: one fix 80 m off with `positionSigma` 5. `update` returns `accepted == false`, and the state moves less than 3 m.
  - `testLinesAreSmoothedIndependently`: two lines 500 m apart. The first state of line 2 is within 10 m of its first measurement.
- [ ] **Step 2:** Run `swift test --filter RouteFilterTests`. Expected: build failure.
- [ ] **Step 3: Implement** a constant-velocity Kalman filter. The state is `[e, n, ve, vn]` with a 4×4 covariance matrix, held in small fixed-size arrays (no dictionaries).
  - F = [[1, 0, dt, 0], [0, 1, 0, dt], [0, 0, 1, 0], [0, 0, 0, 1]].
  - Q is the white-acceleration model with `accelerationSigma`.
  - The position update is gated by Mahalanobis distance. After `maxConsecutiveRejections` rejections in a row, the next fix is accepted.
  - The velocity update uses either the Doppler components or (0, 0) when `zeroVelocity` is set.
  - `stepSpeed` scales the current velocity direction to the step speed, as a pseudo-measurement.
  - `smooth` stores the predicted and filtered moments and runs the standard RTS recursion.
- [ ] **Step 4:** Run `swift test --filter RouteFilterTests`. Expected: pass.
- [ ] **Step 5:** Commit: `feat(core): Kalman route filter and RTS smoother`.

When the span is shorter than the window, it is distance ÷ duration at the midpoint.

- **Engine behaviour:**
  - **On each fix:**
    - Drop it if accuracy is worse than 50 m.
    - σ = max(`minPositionSigma`, accuracy), doubled when accuracy is worse than 25 m.
    - Add Doppler velocity when the speed is trusted and `course >= 0`.
    - Apply a zero-velocity update when the existing `isStationary` check says so.
    - Add the step speed (`cadence / 60 × learned stride`) when accuracy is worse than 15 m and the rhythm is fresh. Stride is learned as an EMA of speed ÷ (cadence/60), only while accuracy is 10 m or better.
  - **Recording:** append the `FilterMeasurement` to `filterInputs`. If the update is accepted, the runner isn't stationary, and the point moved at least `minStep` from the last appended point, append a `TrackPoint` from the filtered state and add the step to `distance`.
  - **Evidence:** record evidence for `Int(activeTime)` on every classifier call: each fix and each rhythm sample. A rhythm sample also triggers `runClassifier` with the latest filtered speed.
  - **`finish`:**
    1. `RouteSmoother.smooth(filterInputs)` produces the smoothed states.
    2. Rebuild the track: keep the existing `minStep` and stationary rules, give each line's first point `startsNewLine`, and take altitude from the measurement.
    3. Set `distance` to the last track point's distance.
    4. Segments come from `Resegmenter.labels` with `speeds[i] = TrackMath.speed(atActiveTime: i)`. If there is no evidence, fall back to the live segments re-measured on the new track.
    5. Run `SegmentSmoother.smooth`.
    6. Set `averageCadence` per segment: the mean rhythm cadence over its seconds, falling back to the mean pedometer cadence.
    7. Set `engineVersion = 2`.
  - The engine stays `Codable` (autosave).
