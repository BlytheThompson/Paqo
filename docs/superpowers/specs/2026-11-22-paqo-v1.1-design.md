# Paqo v1.1: Design

Date: 2026-11-22 · Status: approved ("Approve")

## Intent

v1 tracks the owner's sprint–walk runs (sprint as long as possible, walk, repeat). v1.1
makes that tracking more precise, gives the owner much deeper sprint data, and makes sure
their runs can never be trapped in, or lost with, the app.

The why is the same as v1. Other apps put these features behind paywalls even though they
aren't hard to build. Paqo gives them away and uses the iPhone 17 Pro Max's sensors to
measure more precisely than a GPS-only app can.

The owner picked these six features (2026-11-22):

1. **Sensor recorder**
2. **Sharper sprint detection**
3. **Smoother route**
4. **Sprint trends**, in the owner's words: "Include average speeds per sprint, peak speeds,
   just all the useful data you think that someone would need"
5. **Heatmap and replay**
6. **Backup to files**, in the owner's words: "in a format that other people can easily read
   (so csv or json or something comparable, not some weird file type or proprietary stuff)".
   Backups should be **automatic and manual** (owner's choice).

How each feature is built was left to the builder. The plan below was shown to the owner
before this doc was written, and the owner didn't object.

## Goals

### 1. Sensor recorder
- During every run, Paqo saves the raw sensor streams:
  - every GPS fix, including fixes the engine rejects;
  - motion activity;
  - pedometer;
  - barometer;
  - accelerometer at 50 Hz;
  - pause/resume events.
- The point is to tune detection and filtering against the owner's real runs, on Windows,
  without spending a cloud build on each tweak.
- **On by default** for now, with a Settings switch. Paqo keeps logs for the **last 20 runs**
  and deletes older ones automatically. Settings shows how much storage the logs use and
  has a "Delete all logs" button.
- Each run's summary menu gets **Share sensor log**, which opens the share sheet with one
  zip file. Sensor logs are not part of the backup, because they are too big.
- A **replay tool** runs on Windows: `swift run paqo-replay <log folder or zip>`.
  - It feeds a log through the same `RunEngine` code the phone uses.
  - It prints distance, moving time, a sprint/walk table (start, duration, distance,
    average and peak speed) and the totals.
  - It accepts threshold overrides, so settings can be compared on the same run.
- When the owner sends a log, they'll say in chat what really happened (for example,
  "8 sprints, phone in left pocket"). There are no markers to tap during a run.
- **Re-process from the sensor log** (owner's choice: "Yes, add reprocess"). After a tuned
  build is installed, runs that still have a sensor log can be run again through the
  current detection and filtering.
  - In a run's summary menu, **Re-process** shows before and after (distance, sprint
    count, peak speed, average sprint speed) and asks **Replace** or **Cancel**.
  - Settings › Sensor logs shows "N runs were recorded with older settings" and a
    **Re-process all** button. It shows the same before/after list, then **Replace all**.
  - What a re-processed run keeps: its id, name, start time and Apple Health flag.
  - What gets rebuilt: the track, segments, distance and all stats, along with the run
    index, Records, Trends, the heatmap cache and the auto-backup copy.
  - What doesn't change: the Apple Health workout keeps its original numbers, and the
    confirmation says so.
  - Re-processing uses the same replay code as `paqo-replay`. Replaying a log with
    unchanged settings must reproduce the original run exactly, and a test checks that.

### 2. Sharper sprint detection
- **Accelerometer step rhythm.** From the 50 Hz accelerometer, Paqo works out two things
  every 0.5 s:
  - step cadence, from the periodicity of acceleration magnitude, which works in any
    orientation;
  - impact intensity.
  These become new votes in the classifier. While the accelerometer is fresh it replaces
  the pedometer's cadence vote, so cadence isn't counted twice. The pedometer still
  provides step totals.
- **Faster live switching.** The aim is about 1–1.5 s instead of v1's 3–4 s. Starting
  values: 1.5 s to switch to sprint, 2 s to switch to walk.
- **Whole-run re-segmentation on finish.**
  - Paqo keeps a per-second evidence timeline during the run (activity, rhythm cadence,
    intensity, speed).
  - When the run finishes, it labels the whole run at once with a two-state hidden Markov
    model (Viterbi), using a penalty for switching. This looks both forwards and
    backwards, so sprint boundaries in the summary land within about a second.
  - v1's blip rules still apply afterwards: sprints shorter than 5 s or 15 m become walks,
    and walks shorter than 5 s between sprints are merged into the sprint.
  - The live screen uses the fast live labels. The summary uses the re-segmented ones.
- All thresholds are starting guesses, to be tuned from the owner's logs.

### 3. Smoother route
- **Kalman filter.** A constant-velocity Kalman filter in local east/north meters replaces
  "join accepted fixes with straight lines".
  - Inputs are GPS position, weighted by `horizontalAccuracy`, and GPS velocity (Doppler
    speed plus course), weighted by speed and course accuracy. This needs `course` and
    `courseAccuracy` added to `LocationSample`.
  - When steps or activity say the runner is standing, Paqo applies a zero-velocity update,
    so the line holds still at traffic lights.
  - When GPS is poor (accuracy worse than about 15 m) but the step rhythm is good, Paqo adds
    a speed measurement equal to cadence × stride length. Stride length is learned during
    the same run from stretches with good GPS.
  - Gating:
    - fixes worse than 50 m are ignored;
    - fixes between 25 and 50 m count with low weight;
    - single outliers are rejected by innovation gating, which replaces the hard 12.5 m/s
      rule.
- **Live:** the live map and distance use the filtered positions.
- **On finish:** a Rauch–Tung–Striebel smoother runs a backward pass over the stored filter
  states. The run's saved track (positions, speeds, cumulative distance) is rebuilt from the
  smoothed states. Segment distances, splits and best efforts are all derived from that
  track. The summary's distance may be slightly different from the last number on the live
  screen, usually by less than 1%.
- Pauses still break the line and add no distance. The filter restarts at each resume.
- **Old runs are not reprocessed.** They have no raw data, so they keep their v1 tracks.
  New runs will usually come out a little shorter than v1 would have measured them, because
  GPS wobble no longer adds distance.

### 4. Sprint trends
**Per sprint**, shown in each run's summary and saved with the run:

| Metric | Definition |
|---|---|
| Average speed and pace | |
| Peak speed | The highest speed held for 2 s, from the smoothed speed, so one GPS blip can't set it. This replaces v1's 3-point median for new runs. |
| Distance and time | |
| Time to peak | Seconds from the start of the sprint to its peak speed |
| Average cadence | spm. New runs only. |
| Climb | Elevation gained during the sprint |
| Rest after | Duration and distance of the walk that follows |
| In-sprint fade | Average speed in the last third of the sprint compared with the first third |

**Per run**, shown in the summary as a sprint stats grid and kept in the run index so trends
never need to load full tracks:

- sprint count;
- total sprint time and total sprint distance;
- sprint share (% of moving time spent sprinting);
- average sprint time and average sprint distance;
- average sprint speed (total sprint distance ÷ total sprint time);
- fastest and slowest sprint (by average speed);
- peak speed;
- average rest: walks between the first and last sprint only, so warm-up and cool-down
  walks don't count;
- work-to-rest ratio (total sprint time ÷ total time spent resting between sprints);
- run fade: average speed of the last third of sprints compared with the first third.
  Needs at least 3 sprints;
- average sprint cadence;
- average time to peak.

**Charts and screens:**
- **Fade chart in the summary:** one bar per sprint for average speed, with a marker for
  peak speed, so it's easy to see where the owner slows down.
- **New Trends tab.** Tabs become Run, History, Trends, Records, Settings.
  - **Range:** 4 weeks, 3 months, 1 year or All. Buckets are weekly for the first two
    ranges and monthly for 1 year and All.
  - **Cards:** each has a headline number for the range, its change against the previous
    range of the same length, and a chart. There are cards for:
    - distance and run count;
    - average and peak sprint speed;
    - sprints per run;
    - average sprint time and distance;
    - average rest and work-to-rest ratio;
    - sprint share;
    - run fade;
    - sprint cadence.
  - A metric that doesn't exist for old runs, such as cadence, only uses the runs that have
    it.
- **Records** gains one entry: fastest sprint by average speed (sprints of at least 10 s).

### 5. Heatmap and replay
- **Heatmap.**
  - The History tab gets a **List / Map** switch. Map draws every run's route as a faint mint
    line on a dark, muted map, so the streets run most often glow brightest.
  - A **Sprints only** switch draws only sprint pieces, which shows where the owner goes
    hard. A date range filter offers All, 1 year and 3 months.
  - Routes are simplified (Douglas–Peucker, about 5 m) and cached in their own file, so the
    map stays fast. The cache is filled in for old runs the first time it's needed.
- **Replay.**
  - A **Replay** button on the summary map opens a full-screen player. A marker moves along
    the route, the line fills in mint (sprint) and grey (walk), and the full route shows
    faintly underneath.
  - An overlay shows active time, distance, current speed and pace, and the current segment
    ("Sprint 3").
  - Controls: play/pause, speed (10×, 30×, 60×) and a scrubber. The camera follows the
    marker, with a toggle for an overview.

### 6. Backup to files
- **Formats:** readable, open formats only.
  - **CSV:** UTF-8 with a byte-order mark so Excel opens it correctly, quoted per RFC 4180.
    Columns hold raw metric values (m, s, m/s) plus formatted columns in the owner's unit
    (e.g. `distance_mi`, `avg_pace_per_mi` "9:03").
  - **JSON:** pretty-printed, full key names with units in the name, ISO 8601 dates.
  - **GPX 1.1:** the open route format that Strava, Garmin and Google Earth import.
- **Layout:**
  ```
  Paqo Backup/
    README.txt            what each file and column means, units
    runs.csv              one row per run
    sprints.csv           one row per sprint across all runs (with the rest that followed)
    runs/2026-11-22-0712-morning-run.json   full run, lossless (route, segments, pauses)
    runs/2026-11-22-0712-morning-run.gpx    route only (one track segment per pause-free line)
  ```
  The JSON per run is self-describing (`"format": "paqo-run", "version": 1`) and holds
  everything in `Run`, so import can rebuild the run exactly.
- **Manual export:** Settings › Backup › **Export all runs** builds `Paqo Backup
  2026-11-22.zip` in the layout above and opens the share sheet (Save to Files, etc.).
  The zip is stored without compression, so the iPhone Files app and Windows Explorer can
  both open it.
- **Automatic backup:**
  - Settings › Backup › **Auto-backup folder** lets the owner pick a folder once with the
    system folder picker, for example in iCloud Drive or OneDrive, so it also shows up on
    their PC. Paqo keeps a bookmark to it.
  - The folder holds the same layout, unzipped. Paqo only ever touches the run that changed
    and never "syncs the folder to match the app", so a freshly reinstalled, empty Paqo
    can't shrink or wipe an existing backup. (Builder's call.)
  - **When a run is saved or renamed:** Paqo writes or overwrites that run's JSON and GPX.
    In `runs.csv` and `sprints.csv`, it replaces that run's rows by run id. All other rows
    stay as they are.
  - **When a run is deleted:** Paqo moves its JSON and GPX into `Paqo Backup/deleted/` and
    removes its rows from the CSVs. Paqo never permanently deletes anything in the backup.
    Import skips `deleted/` unless the owner picks that folder directly.
  - **If a CSV is missing or unreadable:** Paqo rebuilds it from the JSON files in the
    folder, not from the app's own runs.
  - Settings shows "Last backed up …". If the folder can't be reached (stale bookmark,
    provider offline), Settings shows that and asks the owner to choose the folder again.
    Runs that failed to back up are retried on the next save.
- **Import:** Settings › Backup › **Import runs** opens a document picker. It accepts:
  - a backup folder;
  - a Paqo backup zip (store-only);
  - individual `.json` run files.
  It skips runs that are already in Paqo (same id), then reports "Imported 12 runs, 3 were
  already here." If a zip uses compression (for example, one re-zipped on Windows), the
  error message says to unzip it in the Files app and pick the folder instead.

## Non-goals (not in v1.1)

- Exporting a single run from its summary
- Importing GPX or other apps' formats
- Uploading to Strava
- Cloud sync between devices
- Editing sprint/walk segments by hand
- Updating Apple Health workouts after a run is re-processed
- The parked list from v1: voice updates, auto-pause, heart rate, treadmill mode, goal runs,
  pace alerts, intervals, Apple Watch

## Anti-goals

- **Real sensor logs or backups in the public GitHub repo.** They contain GPS routes,
  including where the owner lives. They live in a gitignored folder (`private/`) on the PC
  and are never committed. Test fixtures are synthetic.
- **A backup step that can delete or empty an existing backup** because the app's local data
  is missing.
- **Proprietary or unreadable file formats.**
- **A heavier, slower or battery-hungry app.**
  - Logging is buffered and written off the main thread.
  - The accelerometer runs at 50 Hz, not 100 Hz.
  - The heatmap draws simplified routes.
  - The live screen stays as light as v1.
- **Losing or corrupting existing v1 runs during the upgrade.**

## Constraints

- These are the same as v1:
  - Windows-only development; anything not touching Apple frameworks lives in `PaqoCore`
    and is unit-tested locally.
  - iOS builds on GitHub Actions run only when the owner gives the go-ahead.
  - The app is sideloaded with a free Apple ID, so there is no iCloud entitlement.
- The repo is now public. Standard GitHub runners are free for public repos, but builds
  still need the owner's go-ahead.
- Folder access for auto-backup has to work without an iCloud entitlement. The system
  document picker plus a bookmark does.
- The accelerometer has to keep delivering in the background. It does, because background
  location keeps the app running during a run.

## Approaches considered

| Area | Chosen | Alternatives and why not |
|---|---|---|
| Sprint detection | Accelerometer rhythm and intensity as live votes, plus whole-run Viterbi re-segmentation on finish | Accelerometer live only: simpler, but boundaries stay ~1–2 s off. Core ML activity model: needs labelled training data we don't have. |
| Route | Kalman filter (GPS position + Doppler velocity + zero-velocity + step-speed), plus an RTS smoother on finish | Moving-average smoothing: cuts corners and lags. Map-matching to paths: needs an external map service, which breaks "no accounts, works offline". |
| Sensor log format | A folder of CSV files per stream plus `meta.json`, zipped to share | One JSON Lines file: about twice the size. Binary: smallest, but unreadable. |
| Backup | Automatic folder mirror plus manual zip export, with import (owner chose "Auto + manual") | Manual only: simpler, but a forgotten export means lost runs after a bad reinstall. |
| Heatmap | Translucent polylines in MapKit for SwiftUI | Rasterised density tiles: truer heatmap at very high run counts, but needs an `MKMapView` bridge and much more code. Revisit if hundreds of runs make the map slow. |
| Where trends live | A new Trends tab | Inside Records: Records is about bests, trends are about change over time, and it would get crowded. |

## Technical design (builder's calls)

- **Code placement.**
  - `PaqoCore` (Foundation only, unit-tested on Windows) holds all new logic:
    - the step-rhythm analyser;
    - the classifier changes and the Viterbi re-segmenter;
    - the Kalman filter and RTS smoother;
    - sprint and run stats;
    - trend bucketing;
    - route simplification and the heatmap cache;
    - the replay timeline (state at any active time);
    - the sensor log reader and writer formats;
    - the CSV, JSON and GPX writers;
    - the paqo-run JSON reader;
    - a store-only zip writer and reader (with CRC-32).
  - `PaqoSensors` gains an accelerometer service (`CMMotionManager`, 50 Hz, background
    queue, delivered in 0.5 s batches) and `course`/`courseAccuracy` on `LocationSample`.
  - A new executable target, `paqo-replay`, depends on `PaqoCore` only.
- **Sensor log files.**
  - One folder per run: `Application Support/Paqo/sensor-logs/<run-id>/`.
  - It contains `meta.json` (app version, engine configuration, device model, start time)
    and one CSV per stream: `gps.csv`, `activity.csv`, `pedometer.csv`, `altimeter.csv`,
    `accel.csv`, `events.csv`.
  - Timestamps are Unix seconds with millisecond precision. Accelerometer uptime timestamps
    are converted to wall-clock time.
  - Rows are appended through a buffered writer, so a crash mid-run keeps everything up to
    the last flush.
  - Expected size is about 6 MB per hour, mostly accelerometer data.
- **Data model.** New fields are optional, so old run files still decode.
  - `RunSegment` gains `averageCadence`, `peakSpeedTime` and `climb`.
  - `Run` gains `engineVersion`. v1 runs have none; v1.1 runs record which detection and
    filter version produced them. The version goes up whenever tuning changes, and that's
    how Paqo knows which runs can be re-processed.
  - **Mixing v1 and v1.1 runs (builder's call).** Records and Trends treat old and new runs
    the same.
    - When the index is rebuilt, old runs' peak speed is recalculated with the 2-second rule
      from the point speeds already in their tracks, so peak speeds compare fairly.
    - Old distances are not adjusted. The difference is about 1%, and only a few v1 runs
      exist.
  - `RunSummary` gains a `SprintStats` value. It is non-optional, so an old index fails to
    decode and the existing fallback rebuilds it from the run files on first launch.
  - The engine's autosave format changes. A run in progress during the app update may not be
    recoverable, which is acceptable.
- **Replay tool output.** Plain text tables, plus `--json` for machine-readable output.
- **Tests (all on Windows, with synthetic data):**
  - **Rhythm analyser:** finds the right cadence (±3 spm) on simulated walking and sprinting
    accelerometer signals, with noise and different amplitudes.
  - **Kalman/RTS:** on a simulated noisy track, the smoothed distance is closer to the true
    distance than the raw distance, and it doesn't drift while stationary.
  - **Viterbi:** recovers simulated sprint boundaries to within 1 s.
  - **Stats and trends:** checked against hand-calculated examples.
  - **Exports:** CSV, JSON and GPX writers are compared with expected output. JSON
    round-trips back to an identical `Run`.
  - **Zip:** a zip written by the zip writer opens with Windows `Expand-Archive`.
  - **Replay tool:** runs end-to-end on a generated log.
  - **Determinism:** a run recorded live and the same log replayed with the same settings
    produce identical runs. Re-processing depends on this.
- **CI:** unchanged. One cloud build at the end, after everything passes locally.

## Left to the builder

- Exact thresholds and filter noise values. These are starting guesses, tuned later from the
  owner's sensor logs.
- Chart styling and layout within the existing look (charcoal background, mint accent,
  minimal).
- Column order and exact column names in the CSVs, as long as the README documents them.
- The simplification tolerance and the heatmap line opacity.
- Backup file naming details, such as how characters that aren't allowed in file names are
  handled.
